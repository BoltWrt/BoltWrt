## 云环境与最少准备

优先 Ubuntu 24.04 amd64 普通用户、区分大小写的本地构建盘。先记录 `uname -m`、发行版、可用 CPU/RAM/磁盘、QEMU 版本和 `/dev/kvm` 的实际可用性。可用 KVM 需实际试运行确认，不能只凭 CPU 型号或虚拟化 flags 判断。没有 nested KVM 可使用 TCG；跨架构客体使用 TCG。若云环境禁用所需 system emulator 或无法提供足够磁盘，记录实际限制及所需前置，不虚报执行。

固件运行可先以 1 vCPU、512 MiB～1 GiB RAM 尝试。**这不是构建资源预算**：包含 Go/Rust/LLVM 的完整构建需要显著更多内存、磁盘和时间。默认从 `-j2` 开始，按实测资源调整，不擅自购买/扩容、不为省资源删产品包或降低 Rust recipe 的完整构建要求。

在这台专用云环境中按缺失项补充依赖，优先已验证的 Ubuntu 镜像。Ubuntu 24.04 常用构建包如下，仍按实际架构核对包名：

```text
build-essential clang flex bison g++ gawk gettext git libncurses-dev
libssl-dev python3 python3-setuptools python3-pyelftools rsync swig unzip
zlib1g-dev file wget curl ca-certificates perl patch diffutils time xz-utils
```

amd64 额外需要 `gcc-multilib g++-multilib`；不要在 ARM64 照抄这两项。运行工具按实际需要安装 `qemu-system-x86 qemu-system-arm qemu-utils ovmf`，用户态补测才需要 `qemu-user-static`；ARM EFI 可核对发行版 `qemu-efi-aarch64`。先查实际工具和固件路径，不硬编码另一台机器的 OVMF 路径。构建以普通用户执行，不能用 `FORCE=1` 绕过 root/依赖失败。

## x86 完整镜像启动

运行前对原始产物计算 SHA256，解压 IMG.gz；每一案例使用独立副本或 qcow2 overlay，原始固件保持只读。VMDK 必须实际由 QEMU 按 VMDK 打开；转换成 raw 后的启动不能单独声称 VMDK 启动通过。`qemu-img info` 记录格式及完整虚拟容量。

最少矩阵是 BIOS IMG、BIOS VMDK、UEFI IMG、UEFI VMDK。BIOS 使用实际 SeaBIOS/PC 引导链；UEFI 使用相配 OVMF CODE 和每 VM 独立可写 VARS，记录固件包版本、Secure Boot 设置及路径。使用配置中已有支持的 VirtIO 或 e1000/e1000e，并记录真实磁盘总线/网卡。**不能用 `-kernel` 直接载入内核绕过 x86 的 GRUB/EFI 链，再把它算完整磁盘启动成功。**

优先串口控制；对每次启动保存 QEMU 命令、串口、进程/超时状态及客体内部启动证据。管理访问使用仅绑定宿主 `127.0.0.1` 的端口转发或隔离本地网络；先观察默认 LAN `10.126.0.1/18` 和实际接口映射，再设置管理通道。QEMU 默认 usernet 子网未必与产品 LAN 匹配，不得为解决访问问题提前改掉待验默认 LAN。不要把 LuCI/SSH 直接暴露到公网。

每个组合至少完成首次引导与一次客体内重启；公共软件用例可在一个明确指定的基准 VM 完整执行，其余组合核对实际启动、rootfs/overlay、版本、默认配置和 Web 可达。不要把 QEMU 进程仍在运行、出现 GRUB 提示或 kernel banner 单独算成系统启动完成。

运行检查包括：

- `/etc/openwrt_release`/BoltWrt 版本、`uname -r`、`ubus call system board`、PID1/procd、根文件系统、可写 overlay、无启动致命错误，并验证重启后状态。
- LAN `10.126.0.1/18`、hostname/NTP UCI 及守护进程状态；不要求实际外部 NTP 对时或 WAN 链路。
- nginx/uwsgi 的真实进程、监听、HTTPS 握手、Argon 页面和 LuCI 登录/提交。使用隔离临时管理密码；证书可在测试中明确接受自签，不能只用静态 HTML 代替完整 LuCI。
- 检查未引入/运行第二套 uhttpd、端口无冲突；新装独立 haproxy init 默认禁用。PassWall2 内部使用 haproxy 与独立 init 启用状态分别观察。
- 观察 `uci-defaults` 的真实退出/重试/服务日志；成功脚本正常清除，失败应可发现。不能仅用 source 检查或之前 native fixture 结果代替。

实际 LuCI 至少覆盖登录、软件包页面的查询/错误可见性、代表性 UCI 页面的读取/保存，以及现有 SmartDNS/DDNS/PassWall2/SQM/UPnP/OpenVPN/ocserv/frpc/WireGuard 页面可加载且对应后端存在。对包管理 UI 按该版实际支持的动作验证，不假定前端实现了所有 CLI 动作；不连接外部服务，不启用未配置的隧道。

最少执行过程：

1. 启动真实 3.1.2 完整 x86 系统，记录版本、opkg 数据库、引导/磁盘方式及原始状态。创建快照，以同一旧系统派生独立升级用例。
2. 在旧客体生成可辨别的受控 UCI：保持管理可达的网络/hostname/NTP/主题及代表性服务配置；只用虚构地址和非生产参数，不需要 ISP/服务账号。创建临时自签测试证书/私钥和安全自定义脚本，记录内容摘要、所有者、权限与实际引用路径，不输出私钥内容。
3. 检查包声明/keep.d 的实际保留边界；范围外脚本/证书的精确路径写入 `/etc/sysupgrade.conf`。用旧系统的备份清单命令和实际备份审阅结果确认，排除旧 opkg/APK 数据库、包二进制、内核模块和整个 overlay，不用盲目的整目录复制。UCI 保存路径不等于目标文件自动入备份。
4. 分别设置独立 haproxy init 为 enabled 和 disabled，使用各自快照执行标准保留配置路径。旧版标准 `10_disable_services` 产生的 marker 与新版 09 hook/10 恢复顺序是待验点；不能人为删除 marker 后声称验证了标准路径。
5. 将匹配模式的 4.0.0 实际固件传入旧 VM，校验摘要，先执行该系统支持的镜像检查，再在客体执行真实保留配置 `sysupgrade`，观察自动重启/必要的 VM 启动衔接。仅离线解包备份并复制到新 rootfs 不算升级；不能用整盘替换加手工复制冒充 sysupgrade。
6. 启动后核对所有受控 UCI、证书、脚本及权限，实际 HTTPS 证书引用、新 APK 数据库/查询、旧 opkg 数据库/二进制未恢复、服务启用意图和迁移日志；再重启一次。手工缺 marker 或 `-n` 的情况按新装语义分别记录，不能替代标准保留配置案例。

至少对一个明确的引导/磁盘组合完成上述两个服务启用意图案例。其余 BIOS/UEFI/IMG/VMDK 的新装启动结果不能外推该组合均完成升级；BIOS↔UEFI 切换、自改分区、扩容/额外数据不默认已测。OpenVPN 2.7.7 的 static-key、compression、topology、DCO/cipher 既有边界见升级文档；可核对受控配置保留/解析，不开展已取消的握手/链路测试。

## ARM 完整系统与 RAX 用户态的分层验证

QEMU 需要与受支持机器匹配的镜像。RAX 的 MT7981 DTS/UART/交换芯片/NAND/eMMC/`fit0` 与 `virt` 不同，**不能把现成 RAX FIT/FIP/preloader 传给 `-M virt` 并宣称可启动 RAX**；仅选择 Cortex-A53、替换 DTB 或有足够 CPU 性能不能解决板型差异。[QEMU ARM 机器要求](https://www.qemu.org/docs/master/system/target-arm.html)、[virt 文档](https://www.qemu.org/docs/master/system/arm/virt.html)。

完整 ARM 软件启动的可行路径是独立辅助 `armsr/armv8` 目标。先阅读仓库 `target/linux/armsr/README`、目标定义和镜像 Makefile，在单独工作区生成辅助配置，固定相同上游/feeds，并保留可适用的 BoltWrt 共同默认及主要用户空间功能。列明为启动 virt 增加的 virtio/console/rootfs 选项、硬件专属删选及实际 manifest。它是测试夹具，不修改两份产品目标文件、不把它永久加入产品矩阵。

现有 `boltwrt-config.py`/`boltwrt-verify.py` 仅接受 x86/RAX 产品目标；不能放宽这些门禁来伪造辅助 ARM 的产品通过结果。辅助配置应自行 `defconfig`、逐项审查实际保留值并记录差异。`aarch64_generic` 与 RAX 的 `aarch64_cortex-a53` 可能不同，核对实际包架构，不能强制混装或混用另一内核的 kmod。

仓库 README 的 initramfs 最小示例可作为首次定位：

```sh
qemu-system-aarch64 -machine virt -cpu cortex-a57 -nographic \
  -kernel openwrt-armsr-armv8-generic-initramfs-kernel.bin
```

最终按实际产物补内存、串口/管理网卡、持久化 rootfs，或使用其 EFI combined 镜像及适配的 EDKII/U-Boot。直接 `-kernel` 在这里仅证明通用 ARM 内核/系统启动；不算 x86 引导链、ARM EFI 或 RAX FIT 验收。initramfs 启动不能证明配置持久化，需持久化根文件系统才验重启保留。完成版本/PID1/默认脚本/APK/LuCI/重启等通用路径，并与 x86 证据单列。

若需要验证实际 RAX APK/ELF，可从同一锁定构建取得 RAX rootfs，在原生 ARM chroot 或 qemu-user 环境运行。记录宿主和客体架构、ELF、APK 输入/签名及命令；不把用户态 chroot 的宿主内核说成 RAX 内核，不把它等同 procd PID1/完整 VM/驱动或板级启动。[QEMU user 模式](https://www.qemu.org/docs/master/user/main.html)。若只做到该回退路径，通用 ARM 完整 VM 仍记录未执行及原因。

## 证据、修复和交付

每一结果按“通过、失败、受阻、未执行、用户缩减范围未执行、板级未覆盖”准确记录，并注明源 commit、配置/产物 hash、实际平台、完整命令、退出码、时间、日志及覆盖范围。首次失败证据保留，修复后的通过绑定到新输入；不能用重跑成功抹掉原始失败，也不重复已稳定、无相关改动的检查。

证据目录放在项目内未跟踪位置，测试私钥、密码、临时 APK 签名私钥、原始大镜像/缓存不要提交或公开。审查后的脚本/配置修复与不含敏感信息的结果文档按功能逐步提交。可用未跟踪 `AGENT.md` 记录续接信息，不把它加入 Git，也不向 `.gitignore` 添加这个文件名。保留原工作环境供续接，不做无关清理。

最终交付至少包括：

- 主仓/Packages/上游与完整锁版本、实际使用的交接和修复提交；本地 develop 合并记录及未推送状态。
- 云主机与 QEMU/加速/固件环境，云端构建结果、manifest/profiles、四种 x86 核心产物及摘要，ARM 辅助配置/产物/包架构。
- 四种 x86 磁盘启动矩阵、完整默认/Web/APK/LuCI 结果、3.1.2 控制样本和真实 sysupgrade 保留结果，原失败与复测证据。
- ARM 完整 VM 与实际 RAX 用户态各自结果及边界；RAX 板级/存储/DDR 仍未覆盖的事实。
- 更新逐项 P0 清单，明确本轮取消项、保留项的实际状态和剩余阻断；不要笼统宣布原始 P0 全部通过。P1 发布资产/更旧版本直升、P2 更新服务/新增设备/UI 继续不在范围。
